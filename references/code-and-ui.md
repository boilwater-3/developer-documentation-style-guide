# 代码、命令行、占位符、文件名、API 参考、UI 元素与图片（Code and UI）

涵盖行内代码字体、代码示例规范、占位符格式、命令行语法、文件名规范、API 参考注释、UI 界面元素与交互动词、快捷键及图片/截图规范。

## 行内代码字体（Code Font in Text）

行内代码字体（用反引号包裹：`` `code` ``）用于标示**需要原样输入或程序字面量**的内容，将代码实体与普通中文正文清晰隔开。
- **绝不在反引号外再套引号**（除非引号本身就是代码字面量的一部分）。
- **中文字符与反引号之间保留一个半角空格**，中文全角标点与反引号之间**不加空格**。

**必须使用代码字体的内容：**
- 属性名与属性值、类名、结构体名、接口名、枚举名、命名空间、包名
- 方法名与函数名（正文中提及方法时，可加上空括号如 `initializeApp()` 或后跟类别名词如“`get_job_status` 方法”，以明确它是可调用符号）
- 命令行工具名（`gcloud`、`kubectl`、`git`、`npm`）、子命令、标志（`--force`）及命令输出片段
- 数据类型（`STRUCT`、`int64`）、布尔字面量（`true`、`false`）、常量值（`"San Francisco"`）
- 数据库表名、列名、语言关键字（`SELECT`、`FROM`）
- 环境变量（`PATH`）、文件名、文件扩展名、目录路径（`pg_hba.conf`、`/etc/postgresql/13/main`）
- HTTP 内容类型（`application/json`）、HTTP 状态码与请求方法（`400 Bad Request`、`POST`）
- IP 地址、端口号、查询参数（`recursive=true`）、DNS 记录类型（`AAAA`）
- HTML/XML 标签名（正文中提及标签名时通常不带尖括号，如 `div` 元素）
- **占位符**（`SUBNETWORK_NAME`）
- 读者需要在输入框中原样键入的文本（如果该值同时作为 UI 选项展示，则使用**粗体 + 代码字体**：如“选择 **`my-net-2`**”）

**绝不使用代码字体的内容：**
- 产品、服务、项目或组织的正式名称（如写“使用 Git 管理版本”，而指代命令时写“运行 `git` 命令”；写“cURL 项目”，命令写 `curl`）。
- 供读者点击访问的网址（应写成带描述文本的 Markdown 超链接）。

**代码元素融入中文句子的语法规范：**
- 不要把 HTTP 方法、命令名或文件名直接当中文动词用，应在后面加上“请求”“命令”“方法”“文件”等类别名词：

| 推荐写法 | 不推荐写法 |
|---|---|
| “若要添加数据，请发送 `POST` 请求。” | “将数据 `POST` 到服务器。” |
| “在调用 `open` 方法之前，不能调用文件的 `close` 方法。” | “对文件进行 `close` 要求你先 `open` 它。” |
| “`ADDRESS` 常量的值定义在 `settings.h` 文件中。” | “`ADDRESS`'s 值定义在 `settings.h` 里。” |
| “服务器返回 HTTP `400 Bad Request` 状态码。” | “服务器返回 400 错误码。”（规范术语为“状态码”） |

## 代码示例（Code Samples）

- **围栏代码块**：在 Markdown 中使用三个反引号（```` ``` ````）并标注语言标识符（如 ```` ```python ````、```` ```bash ````、```` ```json ````）。
- **缩进与行宽**：遵循对应语言的官方代码规范（通常使用 2 个或 4 个空格缩进，禁用 Tab 制表符）；单行代码尽量控制在 **80 字符**以内，避免读者在阅读时需要横向滚动条。
- **省略部分代码的写法**：如果需要在代码片段中省略无关代码，**必须使用对应编程语言的注释语法**（例如 `# 此处省略若干行代码` 或 `// ... 省略初始化逻辑`），**严禁直接在代码里裸写 `...` 或中文省略号 `……`**，因为那会导致读者复制代码后编译/运行报错。
- **生产安全性**：绝不在代码示例中硬编码真实的密钥、Token 或密码；包含必要的 `import` 语句和基础错误处理，确保示例安全可用。
- **代码块引导语**：代码块上方必须有一句引导说明（紧邻代码块时以全角冒号 `：` 结尾）。

## 占位符（Placeholders）

当命令、URL 或代码片段中包含需要读者替换为实际值的变量时：

- **命名格式**：使用含义清晰的**全大写英文字母加下划线（`UPPER_SNAKE_CASE`）**，如 `PROJECT_ID`、`API_KEY`、`CLUSTER_NAME`。不要使用 `apiName`、`api-name` 或 `<api_key>`（除非尖括号是目标语言语法的强制部分）。
- **不加物主代词前缀**：写 `API_KEY`，**不要写** `YOUR_API_KEY` 或 `MY_API_KEY`。
- **不用无意义的 `x`/`xxx`/`foo`/`bar`**：使用能体现业务含义的名称（唯一例外：表示状态码范围的 `2xx`）。
- **必须在代码块后解释每一个占位符**：
  - 仅有 **1 个**占位符时，紧跟代码块写：“请将 `BUILD_ID` 替换为你上一步复制的构建 ID。”
  - 有 **2 个及以上**占位符时，紧跟代码块写一句“请替换以下内容：”，然后按占位符在代码中出现的先后顺序用无序列表逐一解释：

> 请替换以下内容：
> - `PROJECT_ID`：你的 Google Cloud 项目 ID（例如 `my-sample-project-191923`）。
> - `REGION`：资源所在的区域（例如 `asia-east1`）。

## 命令行语法（Command-line Syntax）

- **优先提供可直接复制运行的完整命令**：在供读者复制粘贴的命令块中，**不要混入表示可选或互斥语法的 `[方括号]`、`{花括号|竖线}` 或 `...`**（这些符号只应出现在专门讲解命令语法格式的参考块中）。
- **长命令换行**：长命令可在连字符（`-`）前拆行，续行缩进 4 个空格，并在上一行末尾加上空格和续行符（Linux/macOS Bash 使用 `\`，Windows CMD 使用 `^`，PowerShell 使用 `` ` ``）。
- **不加命令提示符（Prompt）**：在供读者复制的命令代码块中，**不要在行首加 `$`、`#` 或 `>`**，因为读者一键复制时会把 `$` 一起复制进终端导致报错。（仅当同一代码块必须展示本地与远程主机切换等上下文变化时才加提示符，且切勿包含当前工作目录路径）。
- **命令输入与预期输出必须分开**：将要执行的命令放在一个代码块中，将预期输出放在**另一个独立的代码块**中，并在输出代码块上方写：“输出类似于以下内容：”。在输出代码块中，可以使用单独一行的 `...` 来代表省略的大段输出。

## 文件名与文件类型（File Names）

- **文档源码与示例文件名规范**：使用**全小写英文字母、数字和连字符（`-`）**（如 `query-data.html`、`deploy-app.sh`），不要用无意义的 `document1.html`。
- **正文中引用文件名**：使用代码字体并加上“文件”二字（如“打开 `build.sh` 文件”）。
- **提及文件类型时用正式类型名，而非扩展名**：写“一个 PNG 文件”“一个 JSON 文件”“一个 Markdown 文件”“一个 Bash 脚本”，**不要写**“一个 `.png` 文件”“一个 `.md` 文件”。
- **不要把压缩格式名直接当英文动词混用**：写“解压该 ZIP 文件”或“提取该 tar 归档文件”，不要写“将该文件 unzip / untar”。

## API 参考文档注释规范（API Reference Docs）

编写或生成 API 参考文档（类、接口、方法、参数、返回值）时：

- **完整性**：为每个公开的类/接口/结构体、常量、字段、枚举和方法（含所有参数、返回值、异常）提供说明；每个核心类页面顶部最好附带一段 5~20 行的简短用法示例。
- **类/接口首句描述**：简明概括该类的核心用途，不要以废话“本类用于……（This class...）”开头，直接写名词短语或职能描述（如“Activity 内的主工具栏，用于显示标题、导航按钮及操作菜单。”）。
- **方法/函数首句常用动词范式**：
  - 普通操作方法：直接用动词开头（“向列表中添加一条新记录。”“更新指定用户的权限配置。”）。
  - 返回布尔值的方法（Boolean getter）：以**“检查是否……”**或**“判断……是否……”**开头（如“检查当前会话是否处于活跃状态。”）。
  - 普通获取方法（Getter）：以**“获取……”**开头（如“获取当前实例的唯一标识符。”）。
  - 回调方法（Callback）：以**“当……时调用”**开头（如“当网络连接断开时由系统调用。”）。
  - 便捷构造方法：以**“创建……”**开头。
- **参数（Parameters）与返回值（Returns）说明**：
  - 布尔型控制参数：明确写出两个分支的行为（“如果为 `true`，则验证证书链；如果为 `false`，则跳过验证。”）。
  - 布尔型返回值：写“如果……则返回 `true`；否则返回 `false`。”
  - 默认值标注：在参数说明末尾注明“*默认值*：`30`。”
- **废弃（Deprecation）说明**：第一句话必须直接指出替代方案及迁移方法（如“**已废弃**：请改用 `CameraPose` 类。”）。

## UI 界面元素与交互动词（UI Elements）

- **所有 UI 元素名称一律加粗**：包括按钮、菜单、菜单项、对话框、窗口、文本框、复选框、单选按钮、标签页、列表项等（如“点击**保存**”“在**设置**菜单中”）。如果 UI 标签与界面大小写不一致，以界面实际显示的文字为准。
- **不要把 UI 元素名称直接当动词用**：
  - 推荐：“在**名称**字段中，输入账号名称。” / “若要保存配置，请点击**保存**。”
  - 不推荐：“**名称**你的账号。” / “点击以**保存**该设置。”
- **菜单级联路径**：用粗体与 `>` 表示连续菜单选择（如“依次选择**文件 > 新建 > 项目**”）。注意 `>` 仅用于同类的菜单或导航层级串联，不要把窗口、标签页、输入框等不同性质的容器混在一个 `>` 链条里。
- **标准界面容器术语对照**：
  - **窗口（Window）**：桌面应用程序的主窗口。
  - **页面（Page）**：Web 控制台或网站中的子页面（不要把控制台左侧导航切出来的页面误称为“标签页”）。
  - **对话框（Dialog）**：弹出的模态或非模态小窗口——**严禁使用口语化的“弹窗（pop-up）”**。
  - **窗格（Pane）**：窗口内部划分出的功能区域（如“在左侧**导航**窗格中”）。
  - **部分 / 区域（Section）**：页面内带有小标题的一组控件集合。
  - **标签页（Tab）**：仅指真正支持页签切换的标签页控件。
  - **字段 / 框（Field / Box）**：文本输入区域（如“在**用户名**字段中输入……”），通常无需啰嗦地写“文本输入框”。
- **标准 UI 交互动词规范**：
  - **点击（Click）**：桌面端鼠标左键单击（直接写“点击**确定**”，不要写“点击在**确定**上”或“单击**确定**按钮”；右键写“右键点击”，双击写“双击”）。
  - **点按（Tap）**：移动端触摸屏操作（长按写“按住”）。
  - **选中 / 清除（Select / Clear）**：专门用于**复选框（Checkbox）**（写“选中**自动备份**复选框”“清除**只读**复选框”，避免口语化的“勾上/把勾去掉”）。
  - **选择（Select / Choose）**：用于下拉列表、菜单项或单选按钮。
  - **输入（Enter）**：在文本框中填写内容（优先用“输入”，只有强调逐字敲击键盘动作时才用“键入”）。
  - **按（Press）**：仅用于物理键盘按键或硬件机械按钮（如“按 `Enter` 键”）。
  - **开启 / 关闭（Turn on / Turn off）**或**启用 / 停用（Enable / Disable）**：用于开关（Toggle）或功能状态（写“开启 **Wi-Fi** 开关”或“将 **Wi-Fi** 开关切换到开启位置”）。
  - **将指针悬停在……上（Hold the pointer over）**：当需要等待悬浮提示或展开子菜单时使用。
- **图标（Icons）的指代方式**：通过图标的悬浮提示名称（Tooltip / `aria-label`）来指代图标，**切勿描述图标的几何外观**！
  - 推荐：“点击**菜单**。” / “点击**更多操作**。”
  - 不推荐：“点击左上角的三道杠汉堡图标。” / “点击三个小圆点图标。”
- **去掉按钮末尾的省略号**：如果界面按钮上写着 `Browse...`，在文档中只需写“点击**浏览**（或 **Browse**）。”，无需把省略号抄进文档。

## 键盘快捷键（Keyboard Keys）

- 使用代码字体（`` ` ``）或 `<kbd>` 标签包裹按键与组合键：如“按 `Control+C`”或“按 <kbd>Control+C</kbd>”。
- **字母按键统一用大写**：写 `Control+S`，不写 `Control+s`。
- **拼写出完整的修饰键名称**：写 `Control`、`Command`、`Option`、`Shift`，加号 `+` 两侧**不加空格**。
- **跨平台快捷键写法**：“按 `Control+C`（macOS 上按 `Command+C`）。”——**不要写**难以被屏幕阅读器识别的符号如 `Ctrl+C (⌘C)`。
- 如果组合键中包含容易与连字符或加号混淆的标点符号，请用文字说明（如 `Control+加号 (+)` 或说明按下逗号键）。

## 图片与屏幕截图（Images and Screenshots）

- **克制使用截图**：仅在纯文字无法清晰表达空间布局或复杂视觉关系时才配图。不要为了截一个普通按钮而放整张全屏截图（应裁剪到关键局部），因为 UI 改版和语言本地化会让截图极易过期。
- **严禁使用包含纯代码、命令行或终端输出的截图**：代码和终端输出必须使用真实的文本代码块，以便读者复制、搜索并支持屏幕阅读器朗读。
- **格式偏好**：架构图与流程图优先使用矢量图 **SVG**，位图使用 **PNG**；禁用闪烁或无法暂停的 GIF 动图（如需演示连续操作，使用带控制条的视频）。
- **严禁泄露个人身份信息（PII）与真实密钥**：截图中的真实邮箱、手机号、IP、账号 ID 或密钥必须使用 **100% 不透明度的纯色色块完全遮盖**（切勿使用高斯模糊或马赛克，因为模糊和马赛克可被算法还原）。
- **必须提供替代文本（Alt text）**：
  - 每张有信息量的图片都必须提供简明、准确的 `alt` 文本（不超过 150 个字符，且不要以废话“……的图片/截图”开头，直接描述图片传达的信息，如 `![展示负载均衡器将流量分发到三个可用区的架构图](lb-arch.svg)`）。
  - 纯装饰性图片必须保留空属性 `alt=""`。
- **图注与引用**：如需编号，使用“**图 1.** 完整描述句”；在正文中引用时写“如下图所示”“如上图所示（紧邻时）”或“如图 2 所示”，避免使用受屏幕排版影响的“如左图/右图所示”。
