# 英译中实操指南与细分文档体裁规范（Translation and Document Types）

涵盖英文技术文档翻译为中文的核心实操原则，以及 README、教程与快速入门、API 参考、架构设计文档、发布说明等常见文档体裁的结构模板与规则豁免说明。

## 一、英文技术文档英译中规范

翻译英文技术文档时，目标不是逐字还原英文语法结构，而是**准确传达技术语义并符合中文开发者的阅读习惯**。

### 1. 术语处理三原则

- **业界通行、无需强行意译的英文术语（保留英文）**：如 `API`、`SDK`、`CLI`、`Webhook`、`Token`、`Middleware`（或按项目术语表译为“中间件”）、`Pod`、`Namespace`、`Docker`、`Git` 等。保留英文时遵循中英文混排空格规范。
- **已有成熟中文译名的通用概念（统一译为中文）**：如 `latency`（延迟）、`throughput`（吞吐量）、`idempotency`（幂等性）、`rate limiting`（限流）、`concurrency`（并发）、`persistence`（持久化）。同一文档内绝不中英混用或译名摇摆。
- **读者可能不熟悉的新概念或专业缩写（首次中英对照）**：首次出现时采用**“中文译名（英文原词）”**或**“中文全称（英文全称，简称缩写）”**，后文统一使用简洁表达。例如：“采用**熔断器（Circuit Breaker）**模式防止级联故障”。

### 2. RFC 2119 规范性关键词精确对应

翻译规范文档、安全说明或 API 约束时，严禁随意升格或降格原文的约束强度：

| 英文原词 | 规范中文译法 | 注意事项 |
|---|---|---|
| `MUST` / `REQUIRED` | **必须** | 不可弱化为“应该”或“需要” |
| `MUST NOT` | **严禁** / **不得** | 不可弱化为“不要” |
| `SHOULD` / `RECOMMENDED` | **建议** | 除非表示强规范，优先用“建议”替代模糊的“应该” |
| `SHOULD NOT` | **不建议** | 明确属于非强制性的反模式 |
| `MAY` / `OPTIONAL` | **可以** / **可选** | 不可误译为表示不确定性的“可能” |

### 3. 英文长难句拆解策略

1. **拆分后置定语从句**：不要把长定语全部堆在名词前形成多重“的”字链，将其拆为两个顺承分句或独立短句。
   - 生硬直译：“这是一个允许你在不中断正在运行的生产流量的情况下动态更新配置的服务。”
   - 推荐译法：“借助该服务，你可以动态更新配置，且不会中断正在运行的生产流量。”
2. **还原名词化结构为动词**：英文偏好抽象名词（`perform validation of`、`make a modification to`），中文应直接还原为干脆的动词（“验证”“修改”）。
3. **重排条件与目的从句**：英文常把 `if`、`when`、`to ...` 放在句尾，译为中文时按中文逻辑移至句首（“若要……，请……”“当……时，系统会……”）。
4. **保留代码与界面锚点**：代码标识符、命令行标志、错误信息原文、日志字段切勿翻译；如果产品 UI 只有英文界面，操作步骤中保留界面英文原文并加粗（必要时在括号内附中文释义，如“点击 **Settings**（设置）”）。

## 二、常见文档体裁结构与差异化规则

不同体裁的读者诉求不同，在遵循核心风格原则的基础上，应采用对应的组织结构与合理豁免。

### 1. README（项目主页说明）

**读者目标**：在 1 到 3 分钟内判断该项目能解决什么问题、如何安装跑通，以及如何进一步查阅文档。

推荐章节骨架：
1. **项目名称与一句话定位**：开篇直接说明项目是什么、解决什么核心问题（可附精简状态徽章）。
2. **核心特性**：3 到 6 条精炼的无序列表，聚焦开发者可感知的价值。
3. **快速开始（Quickstart）**：提供最短可运行路径（环境要求 → 安装命令 → 最小可用示例 → 预期输出）。
4. **核心配置或常用用法**：列出最高频的参数、命令或环境变量表格。
5. **延伸文档与贡献指南**：链接至详细文档、架构说明、贡献指南与开源许可证。

**体裁豁免**：允许在特性列表中采用更紧凑的短语；顶部可使用简洁的构建/版本徽章（但避免堆砌过多装饰性图标）。

### 2. 教程与快速入门（Tutorial / Quickstart）

**读者目标**：跟着步骤亲手完成一个端到端任务并看到明确结果。

核心要点：
- **目标与前置条件前置**：开头写明本教程的最终产出、预计耗时及所需权限、工具版本或账号前提。
- **每步可验证**：关键步骤后明确告知预期输出或界面变化，帮助读者确认执行成功。
- **路径单一**：只展示最推荐的一条路径，不在步骤中穿插大量原理长篇大论（原理通过超链接导向概念文档）。
- **清理资源与下一步**：如果教程创建了计费资源或临时环境，末尾必须包含“清理资源”章节，并给出“下一步”学习链接。

### 3. API 参考文档（API Reference）

**读者目标**：精准查询接口签名、请求参数、返回值、默认值、边界条件与错误码。

核心要点：
- **绝对客观与无时间依赖**：严禁出现“最新”“即将支持”“目前”等相对时间词。
- **结构高度一致**：每个接口按固定顺序呈现（概述 → 请求方法与路径 / 函数签名 → 请求参数表 → 返回值与字段表 → 常见错误码 → 最小请求与响应示例）。
- **明确边界**：清晰标注必填与可选、默认值、取值范围、速率限制与幂等性说明。

### 4. 架构与设计文档（Design Doc / RFC）

**读者目标**：评审技术方案的合理性、权衡取舍与实施风险。

核心要点：
- **元数据头**：在文档顶部注明作者、状态（草案 / 评审中 / 已采纳 / 已废弃）及更新日期。
- **目标与非目标（Goals / Non-Goals）**：明确方案要解决的问题以及**明确不做**的边界，减少评审分歧。
- **方案对比与权衡**：用表格客观对比备选方案的优缺点，说明最终选型依据，而非只罗列结论。
- **可视化与容错分析**：优先使用 Mermaid 文本图表展示系统拓扑与核心时序，并覆盖失败降级、安全与可观测性设计。

### 5. 发布说明与变更日志（Release Notes / Changelog）

**读者目标**：快速判断本次版本升级带来哪些新能力、是否包含破坏性变更以及如何迁移。

核心要点：
- **规则豁免**：允许并鼓励使用版本时间锚点，每条发布记录必须标明具体版本号与 ISO 8601 日期（如 `v2.4.0（2026-11-11）`）。
- **清晰分类**：按重要程度分组，推荐顺序为：**破坏性变更（Breaking Changes） → 新增功能（Added） → 改进优化（Changed） → 问题修复（Fixed） → 废弃声明（Deprecated）**。
- **面向影响的写法**：不要直接照抄内部 Git Commit 信息；应站在开发者视角说明“改变了什么、影响谁、需要怎么迁移”，破坏性变更和废弃项必须给出明确的迁移示例或替代方案。
