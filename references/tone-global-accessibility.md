# 语气文风、国际化、无障碍访问与包容性语言（Tone, Accessibility, and Inclusivity）

涵盖中文技术文档的语气定调、未来内容与无时间依赖原则（Timeless documentation）、高可读性与跨语言友好性、无障碍访问（Accessibility）、包容性语言及行业黑话处理。

## 语气与文风（Tone）

理想的技术文档语气应当像**一位经验丰富、温和可靠的工程师同事在面对面为你解答问题**：自然、平实、尊重读者、直奔主题。既不端着官腔、堆砌晦涩公文辞藻，也不故作幽默、玩网络烂梗。

**撰写时请避开以下雷区：**
- **居高临下的主观评价词**：严禁使用**“简单地（simply）”“只需（just）”“轻松（easily）”“显然（obviously）”“毫无疑问”“显而易见”“轻而易举”**。对文档作者来说“很简单”的一步，对于正在排查生产故障、焦头烂额的读者来说可能一点都不简单，这类词只会增加读者的挫败感。
- **暗含指责意味的副词**：避免使用**“仔细地（carefully）”“务必正确地（properly）”“彻底地（thoroughly）”**——写“请确保端口配置正确”等于什么都没教；应直接给出可验证的具体标准：“验证端口 `8080` 已开放并正在监听连接。”
- **过度热情、网络俚语与感叹号**：不要用“老铁们！”“酷毙了！”“是不是超级简单？！”“轰！大功告成！”等轻浮表达；正文中不加感叹号 `！`。
- **空洞的公文套话与填充词**：删掉“值得注意的是”“需要指出的是”“众所周知”“在当前的时间节点下”，直接陈述核心事实。
- **“让我们（Let's）”句式**：不要写“接下来让我们一起看看如何配置……”，直接写“配置步骤如下：”或“你可以通过以下步骤配置……”。
- **操作步骤中的“请”字泛滥**：在分步操作指南中，不需要每一步都以“请点击……”“请输入……”开头，直接用干脆的祈使动词“点击……”“输入……”即可（仅在引导句如“若要删除实例，请执行以下步骤：”或请求读者联系支持团队时适度使用“请”）。

文风校准对照：

| 过于随意/浮夸 | 过于生硬/官腔 | 恰到好处（推荐） |
|---|---|---|
| “兄弟们！这个 API 简直太神了，分分钟搞定用户画像！” | “本接口旨在赋能广大开发者对终端用户之偏好数据进行全方位的采集与洞察。” | “借助该 API，你可以收集用户偏好数据。” |
| “然后——砰！直接调一下垃圾回收就完美收工啦！” | “紧接着，系统的垃圾回收机制应当被开发者所触发以实现内存之释放。” | “若要清理内存，请调用 `collectGarbage` 方法。” |

## 未来功能与“无时间依赖（Timeless）”原则

- **绝不提前预告未发布的功能**：除非属于经过正式审批的路线图（Roadmap）或预览版说明，否则切勿在文档中暗示“未来将支持 Windows”“后续版本会修复此限制”。
- **保持参考文档“无时间依赖”**：读者默认文档描述的就是当前版本的真实状态。那些没有绑定具体版本号或日期的相对时间词，过几个月就会彻底过时。因此在产品文档与 API 参考中，**严禁使用**：
  - *目前（currently）、现在（now）、最新（latest）、新（new）、即将（soon）、最终/以后（eventually）、截至本文撰写时（as of this writing）、尚不支持（does not yet support）、原有/旧的（existing/old）*。
- **必须提及新功能时的锚定写法**：将“新”替换为具体的**版本号或发布日期**。例如写“BigQuery 自 2025 年 1 月 14 日起支持资源面板”或“从 v2.4 版本开始支持该参数”，而不是“BigQuery 新增了资源面板”。
- **例外场景**：带明确时间戳的发布说明（Release notes）、变更日志（Changelog）、技术博客，或描述系统运行时的真实时间先后顺序（如“发送关机指令后，虚拟机很快会下线”）。

| 推荐写法（无时间依赖） | 不推荐写法（易腐烂过时） |
|---|---|
| “你可以使用这些子命令配置 HTTP 负载均衡。” | “你可以使用这些全新的子命令配置 HTTP 负载均衡。” |
| “不支持以下命令行选项：” | “目前尚不支持以下命令行选项：” |
| “该软件不支持 Windows 系统。” | “该软件现阶段暂不支持 Windows，未来将会支持。” |
| “此版本的 SDK 已废弃。” | “此版本的 SDK 现已废弃，并且最终将不再受支持。” |

## 高可读性与国际化友好（Global & Clear Writing）

即使编写的是中文文档，你的读者也可能来自不同技术背景，或者文档后续需要被机器/人工翻译为多国语言：

- **用词朴实精准**：用“使用”代替“利用/赋能（utilize/leverage）”，用“启动/开始”代替“开启……之序幕”，用“因此”代替冗长的过渡套话。
- **控制句子长度与修饰深度**：单句尽量控制在 **35~45 个汉字**以内；避免在一个名词前堆砌超过 2~3 个修饰词（例如将“一个混合云原生 DevSecOps 流水线”改写为“混合云环境下的云原生 DevSecOps 流水线”）。
- **保持术语高度一致**：同一个概念在全文中必须使用完全相同的中文译名和英文大小写。切勿第一段叫“存储桶”，第二段叫“对象存储容器”，第三段又叫“Bucket”——术语摇摆会让读者以为这是三个不同的东西。
- **正面表述“能做什么”**：写“即使未指定路径，你也可以继续执行操作”，比双重否定的“缺少路径并不会阻止你继续操作”清晰得多。
- **避开地域文化梗与方言俚语**：不要使用只有特定圈子或地区才懂的比喻、体育术语、节日梗或方言词汇；示例中的人名、地名尽量自然得体（如“张三”“李四”或通用英文名 `Alex`、`Kim`）。

## 无障碍访问（Accessibility）

优秀的文档应当让使用屏幕阅读器（Screen Reader）、纯键盘导航、屏幕放大镜或存在色觉差异的开发者同样能无障碍地获取全部技术信息：

1. **禁用视觉与空间方位词**：
   - 不要写“如上图/下图/左图/右侧所示”“点击页面右上角的按钮”。在响应式布局、小屏设备或语音朗读中，“左边/右边/上面”毫无意义。
   - 改用逻辑顺序词：**“前文 / 上文（preceding）”“下文 / 以下（following）”**，如“参考前文中的架构图”“运行以下命令：”。
2. **不靠颜色、形状或图标外观传递唯一信息**：
   - 不要写“点击绿色的按钮”或“标红的参数为必填项”（色盲或屏幕阅读器用户无法识别颜色），应写“点击**提交**按钮”“带有 `（必填）` 标记的参数”。
   - 不要写“点击齿轮图标”“点击铃铛图标”，应使用图标对应的无障碍标签名称：“点击**设置**”“点击**通知**”。
3. **语义化结构与替代文本**：
   - 严格保持标题层级连续（不跳级），让屏幕阅读器用户能通过标题大纲快速跳转。
   - 每张非装饰性图片都必须提供准确的 `alt` 替代文本；表格不留空白单元格、不合并单元格；绝不用图片代替代码块或表格文字。
   - 链接锚文本必须具备独立语义（杜绝“点击这里”），因为屏幕阅读器用户常通过调出“页面所有链接列表”来导航。

## 包容性语言（Inclusive Documentation）

使用准确、专业、尊重所有群体的技术词汇，摒弃带有历史偏见、能力歧视或攻击色彩的旧习惯用语：

| 避免使用的词汇 | 推荐替代词汇 | 说明 |
|---|---|---|
| `白名单 / 黑名单`（`whitelist / blacklist`） | `允许列表 / 拒绝列表`（或 `阻止列表 / 信任列表`，`allowlist / denylist`） | 语义更直观自明，消除色彩偏见。 |
| `主从`（`master / slave`） | `主节点 / 副本节点`（`primary / replica`）、`控制节点 / 工作节点`（`controller / worker`）或 `主备` | 架构角色描述更准确。 |
| `中间人攻击`（`man-in-the-middle`） | `在途攻击 / 路径劫持攻击`（`on-path attacker`）或 `中间方攻击` | 更准确地反映网络路径机制。 |
| `健全性检查 / 傻瓜式检查`（`sanity check`） | `快速检查 / 完整性检查 / 置信度检查`（`quick check / confidence check`） | 避免使用带有精神/智力评判色彩的词汇。 |
| `哑变量 / 傻瓜值`（`dummy value`） | `占位符 / 示例值 / 测试值`（`placeholder / sample value`） | 表意更清晰专业。 |
| `人天 / 人月` 中的性别词（`man-hours`） | `工时 / 人时 / 人天`（`person-hours`） | 保持性别中立。 |
| `残废 / 致盲 / 脑残 / 疯狂` 等形容系统故障 | `性能降级 / 缺乏可观测性 / 异常波动` | 用精准的工程术语描述系统状态。 |

**处理存量代码与第三方工具中的旧术语：**
- 如果被文档化的底层 API、配置项或命令行本身包含了旧术语（例如配置项字面量就叫 `whitelist` 或 SQL 命令叫 `START SLAVE`），在正文中阐述概念时使用推荐的新术语，并在首次提及时用括号加代码字体标明代码字面量：例如“将用户添加到允许列表（配置项为 `whitelist`）”。

## 行业黑话（Jargon）的处理策略

黑话（Jargon）是指特定圈子里的比喻性行话（如“宠物与牛（pets vs. cattle）”“对齐颗粒度”“赋能抓手”“爆炸半径（blast radius）”“开箱即用”）或含义极度宽泛的词（如滥用“解决方案”）。

按以下优先级处理黑话：
1. **直接用大白话写清楚（首选）**：与其写“召开一次事后验尸会（post-mortem）”，不如直接写“项目结束后，复盘哪些做法有效、哪些需要改进”。
2. **替换为具体的工程术语**：将“爆炸半径（blast radius）”改为**“影响范围”**；将“宠物与牛”改为**“持久化手动维护实例与动态自动化实例”**；将“摄取（ingest）”改为具体的**“导入 / 加载 / 采集”**。
3. **如果该词确实是读者会搜索的行业通行词**：在首次出现时给出简明解释或括号说明——例如“将安全测试左移（即在开发流程的更早阶段执行安全测试）”。
