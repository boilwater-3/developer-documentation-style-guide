# 语言与语法规范（Language and Grammar）

涵盖中文技术文档的人称、语态、时态表示、句式结构、翻译腔消除、代词、所有格/“的”字用法、单复数处理及英文缩略语规范。

## 人称——统一使用第二人称

- **直接称呼读者为“你”（或“您”）**：默认阅读文档的人就是动手执行开发、部署或配置任务的人。
- **严格区分“你”与“用户（User）”**：“用户”专指读者所开发的软件或服务的**最终使用者（End User）**，切勿把正在看文档的开发者称为“用户”。
- **“你”与“您”的选择**：开源项目、开发者社区、内部工程文档推荐使用自然亲切的**“你”**；面向政企客户、商务色彩较强的云服务官方文档可使用**“您”**。但**同一篇文档乃至同一套文档集中必须保持绝对统一**，严禁“你/您”混用。
- **操作指令使用祈使句**：直接以动词开头（如“点击**提交**。”“运行以下命令：”）。
- **第三人称用于系统与最终用户**：描述软件组件、API 或最终用户的行为时使用第三人称（常见于 API 参考文档，如“该函数返回……”“当用户登录应用时……”）。
- **慎用第一人称复数“我们”**：切勿用“我们”或“让我们（Let's）”来包裹读者（如不要写“让我们创建一个实例”）。仅在明确指代文档发布机构/厂商自身，且指代毫无歧义时才可使用“我们”。

| 推荐写法 | 不推荐写法 |
|---|---|
| “以下各节介绍如何创建网站。” | “以下各节介绍我们如何创建网站。” |
| “建议为数据表添加描述信息。” | “让我们给我们的表添加一段描述吧。” |
| “本文档介绍如何为你的组织开发应用。” | “本文档向用户展示如何为他们的组织开发应用。” |
| “当最终用户点击该按钮时，客户端会向你的服务器发送请求。” | “当用户点击按钮时，客户端向用户的服务器发送请求。” |

## 语态——主动语态优先，克制“被”字句

中文技术写作应优先使用**主动语态**或**自然的无主/主谓句**。滥用“被”字句往往是生硬直译英文被动语态（`is done by...`）的结果，不仅读起来拗口，还会掩盖究竟是**读者**、**客户端**还是**服务端**在执行动作。

| 推荐写法 | 不推荐写法（生硬被动/翻译腔） |
|---|---|
| “向服务发送查询请求，服务器会返回确认消息。” | “服务被查询，并且一条确认消息被发送。” |
| “由你向服务发送查询，再由服务器返回确认消息。” | “服务被你查询，确认消息被服务器发送。” |
| “配置文件保存在 `/etc/app/` 目录下。” | “配置文件被保存在 `/etc/app/` 目录下。” |

**可以使用被动语态（或状态描述句）的场景：**
1. **强调受事对象或结果状态**：“文件已保存。”“连接已断开。”（中文里常直接用“已……”而无需加“被”字）。
2. **弱化无需关注的执行者**：“在配置文件中检测到 50 多处冲突。”
3. **动作执行者无关紧要或未知**：“该数据库已于 1 月份清空。”

## 时态与情态——直陈事实，规范使用能愿动词

中文没有英语那样严格的动词词形时态变化，但翻译或撰写技术文档时常出现生硬的“将会（will）”“可能会（may/might）”混用。

- **常规与确定性行为直接陈述**：描述系统、API 或命令的确定性行为时，直接用一般陈述或加“会”，**不要滥用“将会”**。
- **“将 / 将会”仅用于真正的后续或异步动作**：例如“下次运行备份任务时，系统会将该文件归档。”切勿用“将”来暗示未发布的功能。
- **严格区分能愿动词（对应英文 Modal Verbs）**：
  - **可以（can）**：表示具备某种能力或支持某种配置（“你最多可以配置 5 个副本”）。
  - **可能（might）**：表示不确定性或潜在风险（“在高负载下，请求可能会超时”）。
  - **必须（must）**：表示强制要求或前提条件（“调用此接口前，你必须先获取访问令牌”）。切勿用模糊的“应该（should）”来表达强制要求；如果是推荐做法，请明确写**“建议（recommended）”**。

| 推荐写法 | 不推荐写法 |
|---|---|
| “向服务发送查询请求，服务器会返回确认消息。” | “向服务发送查询请求，服务器将会返回一条确认消息。” |
| “如果你发送退订消息，服务器会将你从列表中移除。” | “如果你发送退订消息，服务器随后就将会把你移除。” |
| “为保障安全，建议每 90 天轮换一次密钥。” | “你应该每 90 天轮换一次密钥。” |

## 句式结构——条件、目的与位置前置

将前提条件、适用场景、目标或操作位置放在指令**之前**，这样如果某一步骤不适用于当前读者，读者扫一眼前半句就能直接跳过，无需读完整个句子。

常用句式模板：
- **目的前置**：“若要[实现目标]，请[执行动作]。” / “如需[目标]，可[执行动作]。”
- **条件前置**：“如果[满足条件]，则[产生结果 / 执行动作]。”
- **位置前置**：“在[界面/目录/配置文件]中，[执行动作]。”
- **交叉引用**：“如需了解更多信息，请参阅[链接标题]。”

| 推荐写法 | 不推荐写法 |
|---|---|
| “若要删除整篇文档，请点击**删除**。” | “点击**删除**，如果你想要删除整篇文档。” |
| “如果你的应用部署在以下任一区域，自定义域名可能会增加延迟：” | “自定义域名可能会增加延迟，如果你的应用部署在以下区域的话：” |
| “如需了解更多信息，请参阅[配置身份验证](#)。” | “请参阅[配置身份验证](#)以获取更多信息。” |

## 消除典型中文“翻译腔”

撰写或润色中文技术文档时，务必剔除受英文语法干扰产生的冗余表达：

1. **删掉泛滥的不定冠词“一个 / 一种”**：英文必须写 `Create a VM instance`，但中文写“创建虚拟机实例”比“创建一个虚拟机实例”更干练（仅在强调数量“仅限 1 个”时才保留“一个”）。
2. **拆分多重“的”字长定语**：英文习惯把定语从句放在名词后，直译成中文容易变成“一个用于处理被客户端上传的经过加密的日志文件的服务”。应改写为动词短语或拆成短句：“该服务用于处理客户端上传的加密日志文件。”
3. **精简使动与弱动词结构**：
   - 将“这允许你 / 这使得你能够（allows/enables you to）”改为**“你可以借此……”**或**“支持……”**。
   - 将“进行 + 动词”（如“进行配置”“进行安装”“进行初始化”）直接还原为动词**“配置”“安装”“初始化”**。
4. **避免名词复数强行加“们”**：中文里只有指代人时才偶尔用“们”，切勿写出“服务器们”“实例们”“参数们”。

| 推荐写法 | 不推荐写法（重度翻译腔） |
|---|---|
| “创建存储桶并配置访问权限。” | “创建一个存储桶并且对访问权限进行配置。” |
| “该插件支持将日志实时导出到 BigQuery。” | “这个插件使得你能够将日志们实时地导出到 BigQuery 当中。” |
| “系统会自动重试失败的请求。” | “那些失败了的请求将会被系统自动地进行重试。” |

## 代词与指代清晰性

- **每个代词都必须有明确、无歧义的先行词**：如果句中出现多个名词，“它 / 该 / 其”容易引起指代不明，此时应直接重复名词（如写“该文本不会改变”，而非“它不会改变”）。
- **指示代词后必须跟具体名词**：不要单独使用“这 / 这个 / 该”作主语或宾语。应写“将**此参数值**设为 `true`”，而不是“将**这个**设为 `true`”。
- **性别中立**：指代假设的开发者、管理员或最终用户时，直接用“开发者”“用户”或无性别区分的“他们 / 对方”，切勿使用“他/她”或默认使用带性别偏见的代词。

| 推荐写法 | 不推荐写法 |
|---|---|
| “如果在文本框中输入文字，该文字不会立即生效。” | “如果在文本框中输入文字，它不会立即生效。” |
| “将此配置项的值设为 `true`。” | “将这个设为 `true`。” |

## 所有格与代码符号修饰

- **不要在代码元素后直接加英文撇号 `'s`**：即使在引用代码方法或常量时，也应使用中文结构（如“`wordCount` 方法的返回值”或“由 `wordCount` 方法返回的值”，绝不写 `` `wordCount`'s ``）。
- **减少生硬的“的”字叠加**：当多个修饰语并列时，利用词组自然粘合或调整语序（如写“Google Cloud 控制台监控页面”，而非“Google Cloud 的控制台的监控页面”）。

## 数量与单复数表达

- **不加英文复数后缀**：在中文句子中穿插代码类名或英文术语时，**不要给代码类名加 `s` 复数**（写“多个 `Intent` 对象和 `Activity` 实例”，不写“`Intents` 和 `Activity`s”）。
- **杜绝 `(s)` 或 `（们）` 写法**：不要在中文或英文术语后加 `(s)` 来表示单复数皆可（如不要写“配置端口(s)”），应直接写“配置一个或多个端口”或直接写“配置端口”（中文名词本身不区分单复数）。
- **单位缩写绝不加复数 `s`**：写 `64 GB`、`10 ms`，绝不写 `64 GBs`、`10 mss`。

## 英文缩略语（Abbreviations）引入规范

- **首次出现时的展开规则**：对于读者可能不熟悉的英文缩略语，首次在正文中出现时，应给出**中文全称（英文全称，英文缩写）**或**中文全称（英文缩写）**，随后在后文中统一使用该英文缩写。例如：“建立**边界网关协议**（Border Gateway Protocol，简称 **BGP**）会话……”后续直接写“BGP 会话”。如果首次出现在标题中，不要在标题里展开括号，而应在紧随其后的第一段正文中展开说明。
- **耳熟能详的通用缩写无需展开**：如 `AI`、`API`、`SDK`、`CLI`、`HTTP`、`HTTPS`、`JSON`、`XML`、`HTML`、`CSS`、`URL`、`SQL`、`REST`、`CPU`、`GPU`、`RAM`、`USB`、`PDF`、`MB`/`MiB`/`GB`/`GiB` 等，直接使用即可，强行展开反而累赘。
- **严禁在正文中使用拉丁缩写**：切勿在中文正文中夹杂 `e.g.`、`i.e.`、`etc.`、`vs.`、`aka`。请一律使用规范中文：**“例如”**、**“即 / 也就是说”**、**“等”**（或用“例如”引出非穷举列表）、**“对比 / 与……相比”**、**“又称 / 也称为”**。
- **不使用网络黑话缩写**：正文中禁用 `tl;dr`、`ymmv`、`RTFM` 等非正式缩写；倍数请写“快 10 倍”，不要在散文句中写“10x 提速”。
- **不要把协议或工具缩写直接当动词用**：写“使用 SSH 登录服务器”，不要写“SSH 进服务器”。
