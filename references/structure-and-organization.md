# 文档结构与组织：标题、列表、操作步骤、表格与链接（Structure and Organization）

涵盖标题层级与命名、锚点、列表（有序/无序/描述）、操作步骤（Procedures）、表格设计、交叉引用与超链接及段落结构规范。

## 标题（Headings and Titles）

- **唯一的一级标题（H1 / `#`）**：每个页面有且仅有一个一级标题，且正文中不要再用二级标题重复页面主标题。
- **标题末尾绝不加句号**，也尽量避免在标题中使用复杂的标点符号（如果标题里需要好几个逗号或括号，说明标题太长，需要重构）。
- **任务型标题 vs. 概念型标题**：
  - **任务/操作型章节标题**：直接以**祈使动词**开头（如“创建虚拟机实例”“配置身份验证”），**切勿**写成“正在创建实例（Creating...）”或累赘的“如何创建虚拟机实例”。
  - **概念/参考型章节标题**：使用简洁的**名词短语**（如“存储桶架构概览”“计费与配额说明”）。
  - 同一篇文档中可以根据章节性质混合使用这两类标题。
- **可选章节标注**：如果整个小节属于可选操作，在标题开头加上 `可选：`（如 `### 可选：配置自定义域名`）。
- **标题中不加序号**：不要在 Markdown 标题中手写 `1.`、`1.1`、`一、` 等序号（除非团队工程模板明确要求），标题层级本身已经表达了结构顺序，手写序号在增删章节时极易出错。
- **标题中慎用代码字体，禁用超链接**：尽量用描述性名词短语做标题（写 `## 配置部署文件`，而不是 `## 配置 config.yaml`）；如果必须包含 API 符号或命令名，请加上类别名词（如 `## 使用 gcloud init 命令`）。**严禁在标题文字上添加超链接。**
- **严格的标题层级**：必须按 `#` → `##` → `###` → `####` 逐级递进，**严禁跳级**（如从 `##` 直接跳到 `####`），也不要为了视觉字号好看而滥用标题标签。
- **引导下属子章节**：当二级标题下紧接着多个三级标题且中间需要过渡句时，写“以下各节介绍……”（不要写指代模糊的“本节介绍……”）。

### 标题锚点（Anchors）
- 如需自定义固定锚点，建议使用全小写英文单词加连字符（如 `{: #create-instance }`）或保持稳定的标题文本。修改已有文档标题时，尽量保留旧锚点以防外部链接失效。

## 列表（Lists）

**如何选择正确的呈现容器：**
- 单维度的步骤、选项、特性罗列 → **有序列表**或**无序列表**。
- 术语与定义、参数名与简短说明配对 → **描述列表（加粗引导词 + 冒号）**。
- 每个条目包含 3 个及以上属性维度（如“参数名 + 类型 + 是否必填 + 说明”）→ **表格（Table）**。

**三种列表类型：**
1. **有序列表（`1. 2. 3.`）**：用于必须按先后顺序执行的操作步骤或有明确优先级/排名的条目。
2. **无序列表（`-`）**：用于无先后顺序的选项、特性、前提条件或注意事项。
3. **描述列表（`- **术语**：说明文本`）**：用于讲解配置项、命令行标志（Flags）或核心概念。

**列表核心规则：**
- **单项不成列**：如果只有 1 个条目，请直接写成普通正文段落，不要用列表。
- **必须有完整的引导语**：永远不要在标题下面毫无铺垫地直接丢出一个列表、表格或代码块。引导语必须是一个完整的句子并以全角冒号 `：` 结尾（如“该 API 支持以下操作：”，切勿写半截话如“你可以通过该 API 来：”）。
- **语法结构严格平行**：同一个列表中的所有条目必须采用相同的语法结构开头（全部用动词短语开头、全部用名词短语开头，或全部是完整句子）。
- **列表项句末标点规则**：
  - 如果列表项是**完整的句子**（或包含多个分句），每项末尾均加全角句号 `。`。
  - 如果列表项全部是**单个词、简短名词短语或纯代码字面量**，每项末尾**不加标点**（也不要加顿号或分号）。
  - 如果使用的是“`- **引导词**：说明文字`”结构，冒号后的说明文字通常按完整句处理，末尾加句号 `。`。
- **正文中内嵌列举**：在段落内部列举时使用顿号 `、`；如果前面已经写了“例如”“包括”“诸如”等表示非穷举的词，末尾**不要再叠床架屋地加“等”或“等等”**（或者删掉“例如”，只在末尾保留“等”）。

规范示例：
> 该 API 支持以下操作：
> - 创建资源
> - 替换资源
> - 更新配置
> - 删除实例

> 调用该 API 时，请遵循以下安全规范：
> - 使用 HTTPS 加密所有请求流量。
> - 每 90 天轮换一次访问密钥。

## 操作步骤（Procedures）

编写分步操作指南时，请严格遵循以下范式：

1. **以祈使动词开头**：每个步骤的第一句话都必须直接以动作动词开头（如“点击**更多**，然后选择**下载**。”）。如果整个流程只有 1 步，用无序列表或直接写一段话即可，无需编号 `1.`。
2. **位置与目的前置**：
   - **先写位置，再写动作**：“在 Google Cloud 控制台中，前往**虚拟机实例**页面。”
   - **先写目的，再写动作**：“若要创建新文档，请依次点击**文件 > 新建 > 文档**。”
3. **结果与原因紧随动作之后**（放在同一步骤段落内）：先告诉读者做什么，再说明执行后会发生什么或为什么要这么做。例如：“点击**运行**。查询完成后，页面下方会显示查询结果。”“将私钥保存在安全位置。后续配置 TLS 证书时需要用到该私钥。”
4. **每步只做一件事**：一个步骤只包含一个核心动作（微小的连续菜单点击可用 `>` 合并，如“依次点击**设置 > 高级 > 网络**”）。
5. **可选步骤标注**：如果某一步是可选的，在步骤最开头写 `**可选**：`（如 `1. **可选**：为实例添加标签。`），不要写 `（可选）`。
6. **禁用空间方位词**：不要写“点击上方的按钮”“如左图所示”“见右表”，应写“参见前文示意图”“参见以下表格（仅限紧邻表格时）”“参见表 1”或直接指明 UI 区域名称。
7. **不要用“运行以下命令”凑字数**：引导命令行代码块时，直接说明该命令的**作用**（如写“部署负载生成器：”，而不是干巴巴的“运行以下命令：”）。
8. **单一最佳路径原则**：在操作指南中只提供最推荐的一种做法，不要在同一处把 GUI 点击、CLI 命令、API 调用三种方法混在一个步骤里让读者做阅读理解（如需提供多种方式，可使用标签页或拆分为独立小节）。
9. **复杂步骤的标准内部顺序**：（1）动作说明句 →（2）命令行代码块 →（3）占位符替换说明（“请替换以下内容：”）→（4）补充标志说明 →（5）预期输出代码块（“输出类似于以下内容：”）→（6）输出结果解读。

## 表格（Tables）

- **仅用于二维结构化数据对比或属性说明**：不要用表格来做页面排版，不要把单列列表放进表格。
- **完整的引导句**：表格上方必须有一句完整的说明语（紧邻表格时以冒号 `：` 结尾）。正文中引用表格时优先使用“以下表格（仅限紧邻引导时）”“前文表格”或具体编号“表 1”，切勿把一句话拆成两半夹住一个表格。
- **表头简明且不加句号**：列标题使用简短的名词短语，末尾不加标点。
- **禁止留空单元格**：屏幕阅读器遇到空白单元格时无法向视障读者传达语义，普通读者也会困惑是“漏填了”还是“不支持”。如果某项无内容，请明确填入 `无`、`不适用`（或 `-` 并在表前说明），切勿留白。
- **不合并单元格**：在 Markdown 和 HTML 表格中避免使用跨行/跨列合并（`rowspan`/`colspan`），合并单元格会严重破坏屏幕阅读器的朗读逻辑和移动端响应式展示。

## 交叉引用与超链接（Cross-references and Links）

- **使用具体、有描述性的链接锚文本**：锚文本必须能让读者在不看上下文的情况下也明白点击后会跳转到哪里（通常直接使用目标页面的标题或核心主题词）。
  - **绝对禁止**使用“点击这里”“此处”“本文档”“这篇博客”或直接裸露一长串 URL 作为链接文本。
- **标准引导句式**：“如需了解更多信息，请参阅[负载均衡与扩缩容](#)。” / “有关任务调度的详情，请参阅[使用 Cloud Scheduler 调度任务](#)。”
- **当链接文本包含缩写时**：如果在此处首次引入缩写，将全称和缩写都包含在链接方括号内，如 `[Google Kubernetes Engine (GKE)](url)`。
- **告知非预期跳转行为**：如果点击链接会直接下载文件或打开外部格式，请在链接文本末尾注明文件类型，如 `[下载架构白皮书（PDF）](url)`。
- **标点符号放在链接外部**：引号、逗号、句号等标点应放在 Markdown 链接 `[文本](url)` 的外面，且不要给链接文本额外加双引号或书名号。

| 推荐写法 | 不推荐写法 |
|---|---|
| “如需了解更多信息，请参阅[负载均衡与扩缩容](#)。” | “想了解更多？请[点击这里](#)！” |
| “你可以参阅[将标题设为链接目标](#)来配置锚点。” | “关于锚点配置，请参阅[这篇文档](#)。” |
| “你可以使用 [Cloud Scheduler](url) 管理定时任务。” | “详情见 `https://cloud.google.com/scheduler/docs`。” |

## 段落结构（Paragraph Structure）

- **一段一意，开门见山**：每个段落只围绕一个核心观点展开，并将**最关键的结论或前提放在段落的第一句话**，方便习惯快速扫读的开发者抓取重点。
- **控制段落长度**：如果一个段落超过 5~6 句话（或超过 200 个汉字），通常包含过多信息，请将其拆分为更小的段落或转化为无序列表，避免出现令人窒息的“文字墙（Wall of text）”。
- **不在段落中间硬换行**：在 Markdown 源码中，如果团队构建工具会将单次换行渲染为 `<br>`，请保持同一段落内自然流式换行，不要在句子中间随意插入硬回车。
